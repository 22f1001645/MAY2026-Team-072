Every downstream Phase 2 behaviour — rotation, reuse detection, the grace window, cold-boot session resolution, the view switcher's authenticated render — sits behind this one broken call.

It wires one real path (login → refresh → rotate → authenticated `/auth/me`) through every layer this phase touches — repository, app factory, controller, service, test fixtures — and proves it with a runnable end-to-end test. Nothing else in Phase 2 is verifiable until this path is green.

Output: a working refresh/logout path, the first Phase 2 backend test module, and the cookie-aware fixtures every later plan's integration tests depend on.

**The one fatal defect** (reproduced 2026-08-12 against `TestConfig` with a real `test_client`):

`POST /api/v1/auth/refresh` → `500 {"error":"Internal server error","code":"internal_error"}`, raised from
`app/__init__.py:51` — `AttributeError: type object 'BlocklistRepository' has no attribute 'is_jti_blocked'`.
`BlocklistRepository` defines exactly `family_revoked`, `by_jti`, `add_entry`. `is_jti_blocked` is referenced once and defined nowhere.

**The second defect, structural:** `auth_controller.refresh` is decorated `@jwt_required(refresh=True, verify_type=False)`. Two problems. (1) It is missing `skip_revocation_check=True`, so once `is_jti_blocked` exists the loader will raise `RevokedTokenError` during decode on any replayed token — before the view body runs — making the whole reuse-detection and grace-window block in `auth_service.refresh` unreachable dead code. (2) `verify_type=False` disables the check that the presented token is actually a refresh token, so an access token in the `Authorization` header is accepted at the refresh endpoint (token-type confusion, threat T-02-14 below).

**The third defect, and the reason removing `verify_type=False` is not sufficient on its own.** `JWT_TOKEN_LOCATION` is `["headers", "cookies"]`, and `_decode_jwt_from_request` breaks on the **first** location that yields a token — it does not prefer the one matching the required type. `frontend/src/lib/api.ts` attaches `Authorization: Bearer <access>` to every request whose in-memory token is set, including `/auth/refresh`. So the moment the access token expires and the client calls refresh, the server reads the **expired access token from the header** instead of the valid refresh cookie and fails the request — precisely when refresh is needed. Today `verify_type=False` masks the type mismatch but the expiry still raises. The fix is to pin both cookie endpoints to the cookie location: `locations=["cookies"]`. This is the server-side, authoritative form of the fix and needs no client change to be correct.

**Out of scope, present in the tree:** commit `f2c127e` bundled a "Phase 9 admin analytics" feature (`frontend/src/pages/OrganiserAnalytics.tsx`, the `/admin/organiser-analytics` route, organiser endpoints in `analytics_controller.py`). It is unrelated to AUTH-01..04 and DASH-01. **Do not extend it, do not test it, do not refactor it.** It is a candidate for its own backlog phase; leave it exactly as it is.

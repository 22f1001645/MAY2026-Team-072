# Pitfalls Research

**Domain:** Adding an organiser-dashboard feature set (dual-role switching, refresh-token auth, activity-scoped teams/tasks, org profiles, timeline+feedback, AI campaign content, progression gating, event chat/polls, QR check-in) to an existing POR-RBAC + Flask-JWT + SQLAlchemy + React SPA system with no migration tooling.
**Researched:** 2026-08-02
**Confidence:** HIGH for codebase-grounded pitfalls (read directly from source), HIGH for auth/migration pitfalls (verified against official docs + 2026 CVEs), MEDIUM for realtime/AI pitfalls (verified against official docs + multiple credible sources, but Ekatva's deployment target is unconfirmed).

> **Phase labels used below.** The roadmap does not exist yet, so pitfalls map to topic-named phases the roadmap author can rename:
> **P0** Migration Foundation · **P1** Auth (refresh/access) · **P2** Dashboard Switcher · **P3** Teams & Tasks · **P4** Org Profile & Social Links · **P5** Timeline & Feedback · **P6** QR Check-in · **P7** AI Campaign Creator · **P8** Progression Gating · **P9** Event Chat & Polls
>
> **The single most important ordering claim in this document:** P0 must ship before any other phase. Eight of the nine features add tables or columns. Today that means running `seed.py`, which calls `db.drop_all()` (`backend/seed.py` lines 39-40). Every phase after P0 that ships without P0 is a phase that cannot be deployed without destroying data.

## Critical Pitfalls

### Pitfall 1: Retrofitting Alembic without a metadata naming convention

**What goes wrong:**
The team runs `flask db init` / `flask db migrate` / `flask db stamp head`, everything works for the first two migrations, and then the third migration - the one that alters or drops a column on SQLite - fails with `ValueError: Constraint must have a name`. The team cannot move forward and cannot roll back, because the naming convention cannot be added retroactively to a database whose constraints were already created anonymously.

**Why it happens:**
Flask-Migrate 4.0+ automatically enables `render_as_batch=True`, which handles SQLite's missing `ALTER` support via a move-and-copy workflow: reflect the table, create a new one, `INSERT ... SELECT`, drop the old, rename. That reflection step needs every constraint to have a name so it can be recreated. Ekatva's models have **25 `db.ForeignKey(...)` declarations and zero named foreign-key constraints**, plus auto-named indexes from `index=True`, and **no `naming_convention` anywhere in `backend/app/`** (verified by grep). Only four constraints are named: `uq_member`, `ix_activity_feed`, `uq_reg`, `uq_fee`. SQLAlchemy applies the naming convention at `Table` *construction* time, so it has to be in place before the metadata is built - not after.

**How to avoid:**
As the very first commit of P0, before `flask db init`:
1. Give `db` an explicit metadata naming convention in `backend/app/extensions.py`:
   ```python
   from sqlalchemy import MetaData
   convention = {
       "ix": "ix_%(column_0_label)s",
       "uq": "uq_%(table_name)s_%(column_0_name)s",
       "ck": "ck_%(table_name)s_%(constraint_name)s",
       "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
       "pk": "pk_%(table_name)s",
   }
   db = SQLAlchemy(metadata=MetaData(naming_convention=convention))
   ```
2. Delete the dev SQLite file and re-run `seed.py` once so the dev DB is created *with* named constraints.
3. Generate the initial migration from the now-named schema, then `flask db stamp head`.
4. Add a CI check that fails if `alembic revision --autogenerate` produces a non-empty diff (catches "someone edited a model and forgot the migration").

**Warning signs:**
- Any `flask db upgrade` output mentioning `batch_alter_table`
- `ValueError: Constraint must have a name` or `Constraint <ForeignKeyConstraint> ... has no name`
- An autogenerated migration that drops and recreates a table you did not touch
- The first migration diff containing renames of indexes you never renamed (means the convention was added late)

**Phase to address:** **P0**, first commit, before any other model change in the milestone.

### Pitfall 2: `seed.py` stays the deploy path, so every schema change is a data wipe

**What goes wrong:**
Alembic gets set up in P0, but `seed.py` still calls `db.drop_all()` + `db.create_all()` and is still the documented way to "reset the DB". A team member on P3 (Teams & Tasks) adds an `EventTask` model, runs `seed.py` because that's the habit, and wipes the demo data another team member was using for their P5 screenshots. Worse, this happens once on the deployed instance right before a course demo.

**Why it happens:**
Adding Alembic does not remove the destructive path. Five people are working in parallel on nine features against one repo; the muscle memory of "models changed → rerun seed" is nine months old. `db.create_all()` also silently *no-ops* on existing tables, so a developer who runs it after adding a column sees no error and assumes their column exists when it does not.

**How to avoid:**
- In the same P0 commit, put a hard guard at the top of `seed.py`: refuse to run if `FLASK_ENV`/`ENV` is anything but `development`, and require an explicit `--force-destructive` flag. Print the DB URL it is about to drop.
- Split `seed.py` into `reset_db()` (dev-only, destructive) and `seed_reference_data()` (idempotent upserts of Houses/Regions/Cities that can run against any environment).
- Update `backend/README.md` and `CLAUDE.md` in the same commit so the documented workflow is `flask db migrate` + `flask db upgrade`, not `seed.py`.
- Never call `db.create_all()` in application startup code.

**Warning signs:**
- Anyone says "just re-run seed" in a PR review or standup
- A model diff in a PR with no accompanying file under `migrations/versions/`
- Demo data disappearing between sessions
- A column exists in `models/__init__.py` but `sqlite3 ekatva.db ".schema"` does not show it

**Phase to address:** **P0**, same commit as Alembic setup. Verification: a deliberate attempt to run `seed.py` against a non-dev DATABASE_URL must exit non-zero.

### Pitfall 3: Refresh-token rotation race condition logs users out mid-session

**What goes wrong:**
The SPA loads a page that fires four TanStack Query requests in parallel. The 15-minute access token has just expired, so all four get a 401 and all four call `POST /auth/refresh` with the same refresh token. The first request rotates the token and blocklists the old one. The other three arrive with a token that is now revoked. If the implementation treats "revoked refresh token used" as a replay attack, it revokes the whole token family and the user is thrown to the login screen for doing nothing wrong. If instead it happily mints a new token for each, the refresh-token family **forks** and rotation provides no replay protection at all.

**Why it happens:**
This is a genuine, currently-exploited class of bug rather than a theoretical one: **CVE-2026-1035** (Keycloak) is a TOCTOU race in `validateTokenReuse` where concurrent requests exchange one refresh token for multiple valid access tokens, and **CVE-2026-53517** (Better Auth) is a non-atomic read/validate/revoke/mint sequence that forks the refresh-token family. Flask-JWT-Extended does **not** provide rotation out of the box - the docs give you `@jwt_required(refresh=True)` and a `token_in_blocklist_loader`, and rotation is left as a manual read-revoke-mint sequence, which is exactly the shape that races. Ekatva's frontend makes this near-certain: `frontend/src/main.tsx` sets `staleTime: 30_000`, so a page landing after 30s of idle fires several simultaneous refetches.

**How to avoid:**
1. **Serialise refresh on the client first.** This kills the majority of the problem for near-zero cost. In `frontend/src/lib/api.ts`, hold a module-level `let refreshPromise: Promise<string> | null`. On a 401, if `refreshPromise` is null, create it; otherwise `await` the existing one. Clear it in a `finally`. Every concurrent 401 then shares one network refresh.
2. **Add a server-side grace window.** Store `rotated_at` on the refresh-token row. Accept a rotated token for a short overlap (30-60s) and return the *already-issued* successor rather than minting a new one. This is exactly the `refreshTokenGracePeriod` that Better Auth was asked to add after the CVE. Only treat use *outside* the grace window as reuse.
3. **Make the rotation atomic.** Do the revoke as a conditional UPDATE (`UPDATE refresh_tokens SET revoked=1 WHERE jti=? AND revoked=0`) and only mint if `rowcount == 1`. Do not do `SELECT` then `if not revoked:` then `UPDATE` - that is the CVE.
4. **Decide the reuse policy explicitly and write it down.** For a student community app, revoking the whole family on genuine reuse is the right call, but only if 1-3 are in place, otherwise it will fire on legitimate users.

**Warning signs:**
- Users report "it logged me out when I opened the dashboard" but the token TTL has not elapsed
- Refresh endpoint request count is a multiple of what one-per-session would predict
- More rows in the refresh-token table than sessions
- Any tests that only exercise a single sequential refresh (they will never catch this)

**Phase to address:** **P1**. Verification: a test that fires 5 concurrent `POST /auth/refresh` with the same token and asserts exactly one new refresh token exists afterwards and all 5 callers got a working access token.

### Pitfall 4: The dashboard switcher becomes the authorisation mechanism instead of a view preference

**What goes wrong:**
The switcher is built by storing `active_por` in localStorage and having the frontend render nav from it. Then it creeps: an endpoint starts reading an `X-Active-Por` header, or the refresh flow starts baking the selected POR into the access token as a claim, and now a student can put `"Regional Coordinator"` in localStorage and get organiser surfaces. Even without a real bypass, the *appearance* of a client-controlled role is a finding on a security-graded course project.

**Why it happens:**
The switcher naturally lives in the frontend, and the existing session layer already computes role client-side (`frontend/src/lib/auth.tsx`, `withPor()` maps PORs to a `Role`; `frontend/src/lib/session.tsx` returns it; `Layout.tsx` does `NAV[role]`). Extending client-side state feels like the smallest change. The current `_load_current_user()` in `backend/app/rbac.py` re-reads the user from the DB on every request, so the backend is safe *today* - the risk is a P1 change putting the selected POR into the JWT and a P2 change trusting it.

**How to avoid:**
- Treat the switcher as a **view preference only**. It changes which nav and which dashboard lens renders. It changes zero authorisation decisions.
- Keep `_load_current_user()` resolving PORs from the database on every request. Never move POR resolution into a JWT claim. Note that the existing `role` claim in `auth_service._token()` is already redundant with the DB lookup - do not add more claims of that kind in P1.
- If an endpoint genuinely needs "which org am I acting for" (e.g. creating a proposal on behalf of one of two orgs), pass it as an explicit **resource-scoped request parameter** (`org_id` in the body) and have the server verify the caller holds an active POR on that specific org. Do not pass it as an ambient "current role" header.
- Add a scoped RBAC helper alongside the existing `organiser_required`: `require_por_on(org_id, {allowed_pors})`. The existing decorator is org-agnostic - it only answers "does this user hold an organiser POR anywhere", which is not enough once P4 lets a Secretary edit *an* organisation's profile.

**Warning signs:**
- Any new HTTP header or JWT claim named like `active_role`, `active_por`, `view_as`
- `organiser_required` used to guard an endpoint that mutates a specific org's or activity's data
- A backend test that passes because the test client sets a role in a header
- Nav shows an org the user has no POR on

**Phase to address:** **P2** for the switcher itself; the scoped-POR helper is a **P2 prerequisite** that P3, P4 and P8 all depend on.

### Pitfall 5: The frontend's organiser-POR list is already out of sync with the backend's

**What goes wrong:**
This is not a hypothetical - it is a live bug in the current code that the dashboard switcher will amplify into a support problem. The backend's `ORGANISER_PORS` (`backend/app/constants.py`) has **seven** entries:

```
Regional Coordinator, Society Secretary, House Secretary,
Deputy House Secretary, Event Lead, Technical Secretary, Web Admin
```

The frontend's `ORGANISER_POR_TYPES` (`frontend/src/lib/auth.tsx`) has **five** - it is missing `Deputy House Secretary` and `Web Admin`. So today, a Deputy House Secretary is computed as `role: 'student'` by the SPA, sees no organiser nav, and yet passes `organiser_required` on every backend call. They are authorised but invisible to themselves. When P2 builds a switcher on top of `withPor()`, these users get a switcher with nothing to switch to, and P4 (which is explicitly scoped to "Secretary/Deputy Secretary can edit their org's social links") is built for exactly the role the frontend cannot see.

**Why it happens:**
A `Set` was copy-pasted across the language boundary with a comment saying "mirrors the backend" and then the backend list grew. There is no test asserting the two agree, and there cannot be one without a shared source.

**How to avoid:**
- Delete `ORGANISER_POR_TYPES` from the frontend entirely. Have the backend compute and return the derived surface in `User.to_dict()`: add `"is_organiser": is_organiser(self)` and `"organiser_orgs": [...]` (the orgs where the user holds an organiser POR, each with the POR type). The SPA then renders from server truth and there is nothing to drift.
- If a client-side list is kept for any reason, generate it from a single JSON constants file consumed by both sides, and add a test that fails on divergence.
- Fix this in P2 *before* building the switcher, not after, because the switcher's option list is exactly this data.

**Warning signs:**
- Any hardcoded POR/role string literal in `frontend/src/`
- A user who can hit an organiser endpoint with curl but has no organiser nav
- A comment containing the word "mirrors" next to a constant
- The switcher dropdown showing fewer options than `GET /pors` returns for that user

**Phase to address:** **P2**, as the first task. Verification: grep `frontend/src/` for POR string literals returns nothing outside display labels; a Deputy House Secretary test account sees the organiser view.

### Pitfall 6: QR check-in gets built in the direction that maximises fraud

**What goes wrong:**
The team implements the easy version: the organiser displays one event QR on a screen/slide, students scan it and self-check-in. Within 90 seconds the QR image is in the event WhatsApp group, and every registered student who did not come is marked attended. Attendance is not cosmetic here - `constants.POINTS["attended"] = 30` feeds the leaderboard, and attendance is the denominator for the activity-fee utilisation analytics that admins report on. A community that runs on WhatsApp will leak a static screen QR essentially every time.

The reverse direction (attendee shows a personal QR, organiser scans) has its own version: student A screenshots their QR, WhatsApps it to student B who is physically present, B shows it at the desk, A gets 30 points for not attending.

**Why it happens:**
"Show a QR on the projector" is a five-line feature and "build a scanner" is not. The scan direction is chosen for implementation convenience rather than threat model, and nobody asks "what is a check-in worth?" before choosing. Industry guidance is consistent that a single shared static entry code is the wrong pattern and that codes should be unique per registration and validated server-side in real time.

**How to avoid:**
- **Choose attendee-presents / organiser-scans.** The scan endpoint is then already `organiser_required`, and a scan is an authenticated organiser action rather than an unauthenticated student action. This also matches the existing `Attendance.checked_in_by` column, which records *who* did the check-in and would become meaningless under self-check-in.
- **Make the QR payload a signed, short-TTL token, not a registration id.** Encode a JWT/HMAC over `{registration_id, activity_id, exp}` with a 60-90 second expiry, refreshed by the student's phone while the ticket screen is open. A screenshot is then dead within a minute. This is the standard rotating/dynamic-QR mitigation for replay.
- **Bind the scan to the event and the window.** Server-side, reject if the token's `activity_id` mismatches the scanned event, or if now is outside `starts_at ± window`.
- **Exploit the constraint you already have.** `Attendance.registration_id` is `unique=True` (`backend/app/models/__init__.py`). A second scan of the same registration will raise an IntegrityError rather than double-award points. Catch it and return a friendly "already checked in at HH:MM" instead of a 500 - do not replace it with a check-then-insert, which reintroduces the same race as the known registration capacity bug.
- **Keep the name-search path.** Do not delete `CheckIn.tsx`'s manual flow. It is the fallback for dead phone batteries, no camera permission, and a venue with no signal.

**Warning signs:**
- A design doc phrase like "display the event QR"
- A QR payload that is a raw UUID or a URL containing one
- No `exp` in the QR payload
- `attended` count exceeding the number of people the venue holds, or exceeding scans logged by the desk
- Attendance timestamps clustered in one second (a screenshot got shared)

**Phase to address:** **P6**. Verification: a test that replays a QR token 5 seconds after expiry gets rejected; a test that scans the same registration twice returns 200 with `already_checked_in: true` and exactly one `Attendance` row.

### Pitfall 7: Offline scanning is designed in, then silently drops attendance

**What goes wrong:**
Someone correctly notes that a college venue may have no signal, so the scanner queues scans in localStorage and syncs later. Three failure modes follow: (a) the organiser closes the tab before syncing and 40 check-ins vanish; (b) two organisers at two desks both scan the same student and the sync creates conflicting state; (c) offline scans cannot validate the short-TTL signature or the "already checked in" constraint, so offline mode becomes the fraud bypass for Pitfall 6.

**Why it happens:**
Offline support is added as a robustness feature without anyone specifying what "queued but not synced" means for the points ledger, and it interacts badly with the short-TTL QR design because the whole point of the TTL is server-side validation.

**How to avoid:**
- **Default to online-only for v1** and make the failure loud: if the scan request fails, show a red full-screen "NOT RECORDED - check connection" state and do not advance to the next scan. A visibly failed scan is recoverable by a human; a silently queued one is not.
- If offline is genuinely required, treat the queue as **evidence, not truth**: store scans locally, show a persistent "N scans pending sync" badge that cannot be dismissed, block navigating away with `beforeunload`, and have the sync endpoint accept a batch and return per-item results. Keep the manual roster fallback as the real offline answer.
- Never let offline scans bypass signature validation - queue the signed token itself and validate it on sync, accepting a wider clock skew for queued items with the scan's local timestamp included and signed by the scanner session.

**Warning signs:**
- A "pending sync" count that never reaches zero
- Attendance rows created with `created_at` long after the event
- Anyone proposing to skip the signature check "just for offline"

**Phase to address:** **P6**. Recommended decision: explicitly scope offline OUT and record it in PROJECT.md's Out of Scope, with the manual roster search as the documented fallback.

### Pitfall 8: Naive polling for event chat melts the backend during the exact hour it matters

**What goes wrong:**
Chat is implemented as `useQuery` with `refetchInterval: 3000`. At a 200-person event, that is roughly **67 requests/second for one event**, each of which runs `_load_current_user()` (a `User.query.get`) plus a message query. Flask-SQLAlchemy's default pool is 5 connections. The backend goes down during the live event - the single hour when organisers need broadcasts to work.

**Why it happens:**
Polling is the correct MVP choice for infrequent updates and the wrong one for chat; the code looks identical either way, and the load only appears at the event, never in development with 3 test users. Every 200-attendee event is a synchronised thundering herd because everyone opens the app when the event starts.

**How to avoid:**
- **Do not build free-form group chat.** PROJECT.md already excludes "Direct/group messaging as a WhatsApp/Instagram replacement". The defensible scope is an **organiser-broadcast + attendee-question feed** (append-only, moderated) plus polls. That is a different, far cheaper read pattern than chat.
- **Use Server-Sent Events, not WebSockets, if you need push.** The read pattern is one-to-many broadcast; SSE is one-directional server-to-client, works over plain HTTP, and needs no new protocol on the Flask side. Posting a message stays a normal POST.
- **Verify the deployment target before choosing.** There is a `.vercel/project.json` in this repo. Vercel Functions gained native WebSocket support in public beta (22 Jun 2026) but connections still die at the function's max duration (5 min default, 30 min on Pro/Enterprise in beta), and future connections are not guaranteed to hit the same function instance - so any fan-out needs external state such as Redis. If the Flask backend is on Vercel, both SSE and WebSockets inherit that duration cap and clients must reconnect with exponential backoff. **Confirm where the Flask app actually deploys before committing to a realtime design** - this is the biggest open question in this research.
- **If polling stays** (a legitimate MVP call): cursor-based (`?since=<message_id>`), 10-15s interval not 3s, jittered to break the herd, `refetchInterval` set to `false` when the tab is hidden, and a cheap `HEAD`/etag endpoint so the common "nothing new" case does no message query. Configure `SQLALCHEMY_ENGINE_OPTIONS = {"pool_size": 20, "pool_recycle": 3600}` regardless.

**Warning signs:**
- `refetchInterval` under 10000 anywhere
- Chat endpoint returning the full message list rather than a delta
- No load test at expected attendee count before the first real event
- Backend p99 latency rising during an event

**Phase to address:** **P9**, and it should be **last** in the roadmap - it has the highest infrastructure uncertainty and the least dependency from other features.

### Pitfall 9: Event chat ships without moderation, then a real incident happens on a university platform

**What goes wrong:**
An anonymous or unmoderated message stream is opened between strangers on a platform carrying IIT Madras branding, with no delete, no report, no mute, and no record of who posted what. The first harassment incident is simultaneously a student-welfare problem and an institutional one, and there is no tooling to respond.

**Why it happens:**
Moderation is not a feature request - nobody asks for it in the notes - so it is not in the scope, and chat is treated as a UI problem rather than a safety-surface problem. Polls make it worse if free-text poll options are allowed.

**How to avoid:**
- **Non-negotiable minimum before any chat ships:** every message is attributed to a real user id (never anonymous), organisers of that event can soft-delete any message, any attendee can report a message, an admin view lists reports, and the whole feed hard-closes when the event registration window closes (already the PROJECT.md scope boundary - enforce it server-side, not by hiding the UI).
- **Rate-limit posting.** There is currently **no rate limiting anywhere** in the backend (no Flask-Limiter in `requirements.txt`). Add it in P9 at minimum for message POST, and while you are there for `/auth/login` and `/auth/refresh`.
- **Polls: fixed options authored by the organiser only.** No user-supplied option text. One vote per user enforced by a unique constraint on `(poll_id, user_id)`, not by hiding the button.
- Soft-delete for moderation means you must actually filter it - note the existing bug where `Report` and `Document` define `deleted_at` but no query filters on it. Do not repeat that pattern for messages.

**Warning signs:**
- A message model without a non-null `user_id`
- No `deleted_at`/`deleted_by` on the message model
- Chat visible on an event whose registration window has closed
- No admin surface listing reports

**Phase to address:** **P9**, in the same phase as the chat itself. If moderation cannot fit in the phase, cut chat and ship polls only - polls have almost none of this risk.

### Pitfall 10: AI-generated campaign content invents event facts and gets emailed to students

**What goes wrong:**
The campaign creator generates a mail template. The LLM, filling a plausible-sounding announcement, adds a time ("doors open at 5:30 PM"), a landmark ("near the metro station"), a fee ("₹150 entry"), or a name that was never in the proposal. An organiser skims it, hits send, and 300 students receive wrong logistics under an official-looking Ekatva OS banner. Poster generation is worse because errors are baked into an image nobody proofreads at pixel level, and the poster gets reshared beyond the platform.

**Why it happens:**
Hallucination is structural - the model predicts likely tokens, not verified facts, and is weakest exactly on niche, recent specifics like one meetup's details. The default prompt shape ("write an announcement for this event") invites the model to fill gaps. The generated output *looks* finished, which suppresses proofreading.

**How to avoid:**
- **Template-with-slots, not free generation.** The LLM writes prose *around* a fixed set of server-injected facts. Title, venue, `starts_at`, capacity, org name and registration URL are interpolated by backend code from the `Activity` row **after** the model returns, into placeholders the model is instructed to emit verbatim (`{{VENUE}}`, `{{STARTS_AT}}`). The model never writes a date, time, address, price, or URL.
- **Post-generation validation gate.** Before showing the draft, regex the output for digits-that-look-like-times, currency symbols, and `http` URLs outside the allowlisted registration link. Flag them in the UI rather than silently accepting.
- **Never auto-send.** The generated artefact is always a *draft* that requires an explicit organiser edit-and-confirm step. The confirm action stores who approved it. Do not wire the campaign creator to the existing `broadcast` endpoint without a human gate.
- **Ground the prompt narrowly.** Pass only the structured fields, not "the proposal description", and instruct: "Do not state any fact not present in the provided fields."
- **Mark the artefact.** Store `generated_by_ai: true` + model + prompt version on the record so a bad output is traceable and the drift is auditable (PRD P7).

**Warning signs:**
- A generated draft containing a time, price, or address that does not appear in the `Activity` row
- The word "approximately" or a hedge in generated logistics
- A code path from generate to send with no user-editable step in between
- No stored record of the prompt that produced a given artefact

**Phase to address:** **P7**. Verification: a test that feeds an `Activity` with a null `venue` and asserts the generated output contains no address-like string.

### Pitfall 11: LLM cost and API keys are unbounded on a student project

**What goes wrong:**
Two failure modes. (a) The API key is put in `frontend/src/` or passed to the browser so the SPA can call the model directly, and it is scraped from the deployed bundle. (b) The key stays server-side but there is no per-user or per-event cap, so one user clicking "regenerate" thirty times, or an image-generation loop, burns the team's credit before the demo. Poster/image generation is an order of magnitude more expensive per call than text.

**Why it happens:**
Calling the LLM from the frontend is the fastest way to get a demo working. Cost governance is invisible until the bill arrives, and a course project has no budget alerting. Note that `backend/requirements.txt` currently has **no HTTP client** (no `requests`, no `httpx`), which is a tell that the LLM call has not been designed server-side yet.

**How to avoid:**
- **The key never leaves the backend.** A single `POST /activities/:id/campaign/generate` endpoint, `organiser_required` plus a scoped POR check on that activity's org. Key from environment only. Add the HTTP client to `requirements.txt` deliberately.
- **Meter tokens, not calls.** Store prompt+completion tokens per generation on the artefact row. Enforce a hard per-activity generation quota (e.g. 5 text + 2 image generations per activity) and a global daily cap that fails closed with a clear message rather than silently degrading.
- **Cache aggressively.** Key the cache on a hash of the structured input fields - regenerating with identical inputs should return the stored artefact for free. Organisers click regenerate a lot.
- **Rate-limit the endpoint** (again: no rate limiting exists today).
- **Make the feature degradable.** If the provider is down or the cap is hit, the campaign creator must fall back to a static, hand-written template with the same slot interpolation. The demo must not depend on a third-party API being up.
- Check the existing `.gitignore` covers `.env` before the first key is created.

**Warning signs:**
- Any `VITE_`-prefixed environment variable containing "KEY", "SECRET", or a provider name (Vite inlines these into the client bundle)
- An LLM call in `frontend/src/`
- No token count stored on generated artefacts
- No cap check before the provider call

**Phase to address:** **P7**. Verification: build the frontend and grep `dist/` for the key prefix - must return nothing.

### Pitfall 12: Progression gating is enforced only in the UI

**What goes wrong:**
"Fest-scale proposals unlock once the org completes its meetup milestones" is implemented as a disabled dropdown option in `ProposalNew.tsx`. Anyone can POST `scale: "regional_fest"` directly. Worse, the gate computation is duplicated: the frontend has its own "has 3 completed meetups" logic and the backend has another, and they disagree at the boundary, so an org sees the option unlocked and gets a 403.

**Why it happens:**
Gating reads as a UX affordance ("grey out the option") rather than an authorisation rule. `ACTIVITY_SCALES` is already a plain constant tuple with no server-side eligibility check tied to it, so adding one requires touching `proposal_service`, which feels out of scope for a UI task.

**How to avoid:**
- Implement eligibility as **one server function**, `org_unlocked_scales(org) -> set[str]`, in `proposal_service` or a new `progression_service`. The proposal submit path calls it and rejects ineligible scales with a specific error code. The frontend calls a `GET /orgs/:id/progression` endpoint that returns the same set plus a human-readable "2 of 3 meetups completed" progress object. **One source of truth, two consumers.**
- Define "completed" precisely and in code, not prose: which `Activity.status`, does a cancelled event count, does an event with zero attendance count, is the window rolling or all-time. Ambiguity here becomes a dispute with a real student org.
- Decide up front whether gating is retroactive. If an org's milestone count drops (an activity is archived or revoked), does an already-submitted fest proposal get revoked? Recommendation: evaluate the gate **at submission time only** and never retroactively invalidate - the alternative is an approval workflow that changes state under the admin.
- The existing proposal state machine already has a related hole: quota is only checked on approve, so `changes_requested → approve` can bypass it. Do not add the progression gate only to the submit path if the same bypass applies - check on both submit and approve.

**Warning signs:**
- An eligibility calculation anywhere in `frontend/src/`
- No test posting a locked scale directly to the API
- No definition of "completed meetup" in `constants.py`
- The gate silently passing for admins in a way that hides the bug during testing

**Phase to address:** **P8**, depending on the scoped-POR helper from P2.

### Pitfall 13: Activity-scoped teams and tasks quietly become a second RBAC system

**What goes wrong:**
`EventTask` gets an `assignee_id`, and then someone needs "the assignee should be able to edit the budget line for their task", and now task assignment grants permissions. Two authorisation systems exist (org-wide POR and activity-scoped collaborator), they disagree, and P3 has undermined PRD Principle P3 (permissions follow PORs).

A second, subtler version: the collaborator model allows tagging **any** user, so an organiser tags someone who is not a member of the org, or who left the org last term, and that person now appears on an internal workspace.

**Why it happens:**
"Assignee" and "has permission on" feel like the same concept. PROJECT.md's Key Decisions explicitly says the event-team model is "not a reuse of the org-wide POR system", which is correct, but the corollary - that it must therefore grant *no* permissions - is not stated and will be forgotten.

**How to avoid:**
- Write the invariant down in the phase brief: **collaborator status is an assignment record, never an authorisation grant.** Authorisation for every mutating endpoint continues to resolve through POR. A collaborator who is not an organiser can see their task and mark it done, and nothing else.
- Constrain who can be tagged: enforce server-side that the tagged user has an active `Membership` in the activity's `org_id`. PROJECT.md says "any org member" - enforce the "org member" half.
- Handle the lifecycle: what happens to tasks when the assignee's POR is deactivated, or the activity is archived, or the proposal is revoked? Decide now. Recommendation: tasks are soft-retained with the assignment frozen, and archived activities' tasks become read-only.
- Do not delete `frontend/src/lib/mock.ts`'s `TASKS` array until the persisted version passes an end-to-end reload test - a half-migrated task UI that reads from mock and writes to the API is worse than either.

**Warning signs:**
- Any RBAC check of the form "is the current user assigned to a task on this activity"
- Task assignment to a user with no membership row for the org
- Tasks surviving with a dangling `assignee_id` after a user is removed
- `ManageEvent.tsx` still importing from `mock.ts` after P3 is marked done

**Phase to address:** **P3**, depending on P0 (new tables) and P2 (scoped POR helper).

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| **LLM provider (text)** | Calling from the SPA with a `VITE_`-prefixed key; Vite inlines it into the shipped bundle | Server-side endpoint only; key from OS env; never referenced in `frontend/` |
| **LLM provider (images/posters)** | Treating image generation as the same cost class as text; no per-activity cap | Separate, much tighter quota for images; cache by input hash; static fallback template |
| **LLM provider** | Passing free-text proposal description straight into the prompt, so organiser-authored text becomes prompt instructions | Pass only structured fields; treat all user text as data, delimited and explicitly labelled as untrusted; validate output |
| **Email/broadcast sending** | Wiring campaign generation directly to the existing `POST /events/:id/broadcast` | Generation and sending are two endpoints with a mandatory human confirm between them |
| **QR scanner (browser camera)** | Assuming `getUserMedia` works - it requires a secure context (HTTPS or localhost) and an explicit permission grant that can be denied permanently | Feature-detect, request permission explicitly with an explainer, and always keep the manual roster fallback reachable in one tap |
| **Vercel (if the Flask API deploys there)** | Assuming a Flask process is long-lived: in-memory token blocklists, in-memory rate limiters, background threads, and SQLite file writes all break | Confirm the deploy target first. Any blocklist/limiter/realtime state must be in Postgres or Redis, never in process memory |
| **SQLite (dev) vs Postgres (prod)** | Writing migrations that pass on SQLite and assuming Postgres agrees - batch mode masks real `ALTER` semantics, and `NOT NULL` + `server_default` backfill behaves differently | Run the migration suite against a Postgres container in CI before any phase that adds a non-nullable column |
| **CORS + cookie-based refresh token** | Adding `Set-Cookie` without `supports_credentials=True` on Flask-CORS and `credentials: 'include'` on fetch; the cookie is silently never sent | Change both sides together; test cross-origin from the real Vite dev origin, not from the same origin |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Chat polling at 3s | Backend p99 spikes during events; pool exhaustion errors | Cursor deltas, 10-15s + jitter, pause on hidden tab, or SSE | ~50 concurrent viewers on one event with the default 5-connection pool |
| `attended_count()` / `registered_count()` Python loops | Event list page slows as events fill; memory spikes | Replace with `func.count()` subqueries or a denormalised counter | ~200 registrations per event, or ~30 events on the discover feed |
| Roster fetched whole and filtered in-browser (`CheckIn.tsx`) | Check-in search laggy on a phone at the venue | Server-side `?q=` filter; also needed for the QR fallback path | ~300 registrations |
| No pagination on the discover feed | Feed load time grows linearly | `?limit&offset` + `useInfiniteQuery` | ~50 published events |
| Every request does `User.query.get()` in `_load_current_user()` | Invisible until request volume rises; then it doubles DB load | Fine as-is, but do not add a polling feature on top of it without measuring | Compounds with any polling feature (P9) |
| Refresh storm on tab focus | Refresh endpoint QPS spikes; possible mass logout (Pitfall 3) | Client-side single-flight refresh promise | Any page with 3+ parallel queries after token expiry |
| Unbounded event message table | Chat query slows over a term | Index `(activity_id, created_at)`; hard-close the feed at window end | ~10k messages without an index |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Refresh token stored in localStorage with a long TTL | Upgrades the existing XSS exposure from a 12h token to a multi-week credential | httpOnly cookie scoped to `/auth/refresh`, or short refresh TTL + rotation + reuse detection |
| Rotation implemented as read-check-revoke-mint | Concurrent refresh forks the token family; rotation provides zero replay protection (CVE-2026-53517 shape) | Conditional atomic UPDATE; mint only if `rowcount == 1` |
| Reuse detection with no grace window | Legitimate concurrent refreshes trigger family revocation; users randomly logged out | 30-60s grace window returning the already-issued successor |
| No logout-everywhere / POR-revocation path | An admin deactivates a POR but the holder keeps organiser access until their refresh token expires | POR checks already resolve from DB per request (keep it that way); add an explicit refresh-token revoke on logout and on `deactivatePor` |
| Static event QR displayed publicly | Mass fraudulent check-ins via WhatsApp; corrupts the points ledger and fee-utilisation analytics | Per-registration signed QR with 60-90s TTL, scanned by an authenticated organiser |
| No rate limiting anywhere (still true today) | Credential stuffing on `/auth/login`, refresh-endpoint abuse, chat spam, LLM cost exhaustion | Flask-Limiter on `/auth/login`, `/auth/refresh`, message POST, and the generate endpoint |
| `organiser_required` used for org-specific mutations | Any Event Lead anywhere can edit any org's social links (P4) or any activity's tasks (P3) | Scoped `require_por_on(org_id, ...)` helper introduced in P2 |
| Social links stored and rendered without validation | Stored XSS via `javascript:` URLs; SSRF if the backend ever fetches link previews | Allowlist schemes (`https` only) and known domains; never fetch user-supplied URLs server-side |
| LLM key in a `VITE_` env var | Key extracted from the public bundle | Server-side proxy endpoint only |
| Poll votes hidden client-side rather than constrained | Ballot stuffing on a leaderboard-adjacent feature | Unique constraint on `(poll_id, user_id)` |
| Anonymous chat messages | No accountability path for a harassment incident on a university-branded platform | Every message carries a real `user_id`; organiser soft-delete; report flow |
| Feedback forms without identity or de-duplication | Ratings gamed to inflate an org's progression-gating milestones (P8) | Tie attendee feedback to a `Registration` with `Attendance`; one response per registration |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Switcher shown to users who hold only one role | Confusing dead control for the ~99% majority of 40k students | Render the switcher only when the server says the user has >1 available view |
| Switcher resets to Student on every reload | Organisers re-select on every visit; feels broken | Persist the preference (localStorage is fine - it is a preference, not authorisation) and honour it on load |
| Switching context but keeping the current route | User switches to Student view while on `/organiser/events/:id/tasks` and hits a 403 | Switching always navigates to that view's home route |
| Silent token refresh that briefly renders an error/empty state | Flash of "something went wrong" on every page load after idle | Queue requests behind the single-flight refresh rather than letting them fail-then-retry |
| Forced logout on a genuine concurrent-refresh race | Trust in the platform drops fast; students blame the app | Grace window (Pitfall 3) |
| QR ticket screen that dims or locks | Student cannot get scanned; queue backs up | Request a wake lock / max brightness on the ticket screen; show the registration id as scannable text fallback |
| Scanner with no audible/haptic confirmation | Organiser scans the same person twice, or misses a failure, in a noisy venue | Distinct sound + colour + vibration for success / already-checked-in / rejected |
| Post-event feedback prompt sent to everyone registered | Non-attendees rate an event they did not attend; data is worthless | Prompt only registrations with an `Attendance` row; send it after the event ends, not on registration |
| Dual-sided feedback presented as one long form | Both sides abandon it; the organiser reflection (which feeds the report) is the one that matters | Attendee side: 1 rating + 1 optional free text, in-app, one screen. Organiser side: structured prompts, saveable as draft |
| AI draft presented as finished copy | Organisers send hallucinated logistics without reading | Present as a visibly unfinished draft: editable textarea, "AI draft - verify details" banner, facts highlighted as server-injected |
| Progression gate shown as a disabled control with no explanation | Org leaders think the platform is broken or that they are being blocked arbitrarily | Show the progress explicitly: "Fest proposals unlock after 3 completed meetups (2 of 3)" |
| Chat visible but read-only after the window closes with no explanation | Users think posting is broken | Explicit "this event's chat closed on <date>" state |

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Alembic set up without a naming convention | **HIGH** if data exists, LOW if not | Add the convention, drop and recreate the dev DB, delete `migrations/`, regenerate the baseline. On a live DB this needs a hand-written migration renaming every constraint per table - avoid entirely by doing it first |
| `seed.py` run against a populated DB | **HIGH** (unrecoverable without a backup) | Restore from backup. If none: re-seed reference data, ask users to re-register. Prevention is the only real answer - add the guard in P0 |
| Refresh rotation forking token families | **MEDIUM** | Revoke all refresh tokens (forces one re-login for everyone), deploy the atomic conditional UPDATE + grace window, re-issue |
| Mass logout from over-aggressive reuse detection | **LOW-MEDIUM** | Ship the grace window, communicate, users re-login once. Reputational cost is higher than technical cost |
| Static event QR leaked, fraudulent attendance recorded | **MEDIUM** | Attendance is the input to the points ledger, so it must be reversed: identify attendance rows for that activity created outside the physical window, delete them, and reverse the corresponding points entries. Rebuild leaderboard. Then rebuild the QR properly |
| Hallucinated details emailed to students | **MEDIUM-HIGH** (reputational) | Send a correction broadcast immediately; disable the campaign creator until the slot-template fix ships; document the incident (a course project graded on process benefits from a written post-mortem) |
| LLM credit exhausted mid-term | **LOW-MEDIUM** | Static-template fallback keeps the feature demoable; add caps before re-enabling |
| Chat outage during a live event | **MEDIUM** | Have the existing broadcast/notification path as the documented fallback and tell organisers about it *before* the event; raise the poll interval via config without a redeploy if possible |
| Frontend/backend POR list drift | **LOW** | Delete the frontend list, return `is_organiser` from the API. Cheap now, cheaper than after the switcher is built on top of it |

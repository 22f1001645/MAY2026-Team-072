<objective>
Close the second enforcement checkpoint and open the read surface. `decide()`'s approve branch re-checks eligibility and, per D-01, re-checks the collaborator threshold under its *accepted* definition; a successful approval that makes the org fest-eligible records the PROG-03 unlock marker. A new authenticated GET serves both counts, the derived boolean, the threshold and the unlock list to the two frontend callers.

Purpose: eligibility and consent can both change while a proposal waits in the admin queue — a fest submitted while eligible can have its qualifying regional meetup revoked before an admin ever looks at it. Without the approve-time re-check, PROG-04 is enforced only against the caller who was honest enough to use the form.

Output: the approve checkpoint, the unlock write, the read endpoint, and confirmation that the seeded demo data can actually reach fest tier.

Decisions implemented here:
- D-01: the **accepted** half of the two-point collaborator check — `decide()`'s approve branch counts `COLLAB_ACCEPTED` rows (primary included) against `FEST_COLLAB_THRESHOLD`, mirroring `Activity.is_mega_meetup`'s expression in the service rather than adding a second model property.
- D-02: the accepted-count definition at approve is exactly what makes "6 named but declined" unapprovable, which is the consent guarantee the rejected alternative would have broken.
- D-03: the approve-time re-check is scoped to the activity's own `(org_id, city)` pair, and `record_unlock` keys the marker on the same pair.
- D-04: this plan builds the read endpoint the `ProposalNew` lock-state fetch consumes, returning both counts independently so the "1 of 2 completed" caption is renderable.
- D-05: the same endpoint returns the org's full `unlocks` array with no `city` param — the exact payload the `OrgProfile` banner needs, so no third route is added.
</objective>

## Flagged Assumptions

- **A1 — unlock recorded whenever eligibility newly turns true (option b, adopted).** `record_unlock()` is called at the end of *every* successful approval, guarded by `if fest_eligibility(...)["fest_eligible"]`. The alternative (record only when a `regional_fest` itself is approved) was rejected because it makes the D-05 banner appear one fest *after* the scale card unlocks, so the two surfaces would disagree. Option (b) subsumes (a). Rated `costly` rather than one-way: reversing it means deleting rows from a table nothing reads for authorization, not a migration.
- **A2 — `auth_required` on the read route (adopted).** The stricter `can_manage_org_required` would 403 an admin proposing on behalf of an org, a flow `submit_proposal()` lines 50-51 explicitly permits. The payload discloses nothing not already public in `published_feed`.
- **A4 — no AuditLog row on a refused fest approval (adopted).** No refusal anywhere in `proposal_service.py` writes one, including the quota refusal at line 279. Consistency with the file beats a new pattern in a phase whose whole point is reusing the existing one.

| admin browser -> `POST /api/v1/proposals/<id>/decision` | The only caller who can approve. Eligibility and collaborator consent may both have changed since the proposal was submitted, so the state the admin is acting on is untrusted with respect to time. |

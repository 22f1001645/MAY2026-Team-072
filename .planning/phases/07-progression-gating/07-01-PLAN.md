<objective>
Prove the fest-tier progression gate end-to-end on one path: an ineligible organisation POSTing `scale: regional_fest` is refused 403 `fest_locked` by a server-computed eligibility check, and the same organisation succeeds once its track record is real. Then expand along the submit-side checkpoint to cover the PROG-02 named-collaborator threshold.

Purpose: PROG-04 makes progression an authorization decision. The one thing that must be true before any other Phase 7 work is worth doing is that a direct API call cannot propose a locked scale. Everything else in the phase (the approve-time re-check, the read endpoint, the whole UI) is expansion off this slice.

Output: the threshold constant, the completed-meetup count query, the `progression_service` module that owns the rule, the first of two enforcement checkpoints, and the new test file with its seeding helper.

Decisions implemented here:
- D-01: the **named** half of the two-point collaborator check — `submit_proposal()` counts named organisations (`valid_collab_orgs` + the primary) against `FEST_COLLAB_THRESHOLD`. The accepted half lands in plan 07-02.
- D-02: the rejected alternatives are honoured by omission — no accepted-count check is added at submit (it could never pass on a brand-new proposal), and the named count is not reused at approve.
- D-03: eligibility is scoped per (org, city). `completed_meetups_by_scale` filters on `Activity.city`, and `test_eligibility_is_per_city` pins it.
</objective>

## Flagged Assumptions

These are planner decisions on questions 07-RESEARCH.md left open. Each is one clause of code to reverse.

- **A3 — primary-only counting (adopted).** PROG-01 counts activities where `Activity.org_id` is this org. An org that co-hosted (accepted a collaboration invite on) a local and a regional meetup in a city does **not** unlock. This matches REQUIREMENTS.md's "that org has completed" read narrowly, matches the existing `meetups_in_region_month` precedent, and is the narrower security posture. Reversal is one added clause on the query's join.
- **A2 — `auth_required` on the read route (adopted, implemented in plan 07-02).** Named here because `fest_eligibility()` is written in this plan and is what that route serves.
- **Ordering / adjacency is inapplicable.** `org_progression_unlocks` is unique on `(org_id, city)`, so there is no merge/collide/separate question and no output ordering to specify. The equality boundary that does exist (a second qualifying approval in the same city) is covered as a truth in plan 07-02, not left unresolved.

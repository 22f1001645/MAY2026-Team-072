<objective>
Build the campaign package spine that needs nothing from Phase 4: the singleton
`CampaignPackage` accessor, server-minted registration slugs, custom registration fields, and
real slug resolution so a shared registration link actually resolves to an event page.

Purpose: CAMPAIGN-04 and CAMPAIGN-05 are two of the eight requirements OD-1 marks executable
today. They also establish `_get_or_create_campaign`, which every later campaign write
(poster, mail, push-live) upserts through.

Output: `campaign_controller.py`, the slug/form-field half of `campaign_service.py`,
`ActivityRepository.by_slug_or_id`, a public-preview event detail route, and
`backend/tests/test_campaign_package.py` — the Wave-0 test file plans 05-03, 05-10 and 05-11
extend.
</objective>

  `campaign_service.registration_form`. Promoting — seeding the two core fields as rows — is the
  structurally cleaner move, but AC-23 states the core set is fixed and always present, and rows
  are editable and deletable by definition, so promotion would contradict the requirement it is
  meant to serve.
- **What would force a later promote:** the first requirement to reorder, relabel, translate or
  conditionally hide a core field. At that point the core set stops being a constant and the two
  entries should become seeded, undeletable `RegistrationFormField` rows with an `is_core` flag.
- Recorded here rather than in the code so a Phase 6+ author meets the decision, not the symptom.
</assumption_delta_decision>

<objective>
Close the loop on the admin side and the organisation's own page. The approval queue tells the admin how many collaborators have actually accepted before they click approve, and explains the refusal as a rule when they click anyway. `OrgProfile` shows the organisation the standing marker that it has reached fest tier, and in which cities.

Purpose: PROG-03's requirement is a recorded flag "surfaced as UI messaging" — the marker is worthless if nobody ever sees it. And the approve-time refusal is the one place in the phase where the person being refused did nothing wrong: the collaborators have simply not all replied yet, so it has to read as a status, not a failure.

Output: two in-place page modifications plus the phase's manual verification gate.

Decisions implemented here:
- D-05: the "Sponsorship & outreach tools unlocked" marker surfaces as a banner on `OrgProfile.tsx`, visible to the org's own managers, listing every unlocked city as a chip. Banner only — no notification-on-creation was requested, and no CRM tooling sits behind it.
- D-01: the approval queue renders the **accepted** count, the second of the two definitions, so the admin sees why an approve will be refused before they attempt it.
- D-02: the queue header counts accepted rows rather than named ones, which is precisely the consent guarantee the rejected "named count both times" alternative would have discarded.
- D-04: this plan's `OrgProfile` call reuses the same `useOrgProgression` hook the fest-card lock uses, with no `city` argument — one endpoint and one cache family across both surfaces.
</objective>

<objective>
Close the two authorization holes Phase 5 inherits: volunteer points can currently be awarded
to any user id in the system with no membership check at all, and nothing proves that crew
membership stays confined to its own activity.

Purpose: TEAM-04 is a live privilege-escalation hole in `attendance_service.py` today —
verified this session, there is no membership check of any kind between the 404 and the
`ContributionPoint` write. TEAM-03's behaviour is already correct in `rbac.py`; what Phase 5
adds is the proof that keeps it correct, and the removed-member case (PROB-P4) that nothing
tests today.

Output: the crew guard in `attendance_service.award_volunteer_points`, and three tests in
`backend/tests/test_activity_tasks.py` that go red the moment either boundary erodes.
</objective>

  <action>
Insert the crew guard into `backend/app/services/attendance_service.award_volunteer_points`,
immediately after the existing `event_not_found` 404 and **before** the first
`db.session.add(ContributionPoint(...))`. Query `ActivityTeamMember` filtered by both
`activity_id` and `user_id`; when no row exists, raise
`ApiError("Volunteer points can only be awarded to a member of this event's crew.",
"not_crew_member", 403)`. Placing it before the add is what makes "no ledger row is written on
refusal" true by construction rather than by a rollback.

Do **not** change the route's decorator. `("POST", "/api/v1/events/<activity_id>/volunteer")`
is one of the six frozen `LEGACY_COARSE_ROUTES` entries; swapping `organiser_required` for a
scoped guard would still pass both RBAC gates, but it is a behaviour change with no Phase 5
requirement behind it, and Phase 1 recorded an explicit decision not to retrofit those six.
TEAM-04 is a service-tier authorization rule, and AC-37 says so: "service error → 403 from
endpoint".

Add a docstring line to `award_volunteer_points` naming TEAM-04 and stating that the membership
check is deliberately here rather than in the route, so a future reader does not "simplify" it
upward into a decorator that the frozen-route rule forbids.

Add the three behaviors to `backend/tests/test_activity_tasks.py`. The negative test must
assert the absence of the ledger row, not merely the status code — a 403 that had already
written the row would pass a status-only assertion.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| organiser → `POST /events/<id>/volunteer` | A coarse-guarded legacy route where the *target user id* is attacker-chosen |
| crew membership → org authority | The boundary TEAM-03 exists to keep closed |
| `ActivityTeamMember` row lifetime → access lifetime | PROB-P4: revocation must be immediate |

## STRIDE Threat Register (ASVS L1, block on high)

|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-25 | Elevation of Privilege | `award_volunteer_points` awarding to an arbitrary `user_id` — fully open today to any organiser POR holder anywhere | high | mitigate | `ActivityTeamMember` lookup on `(activity_id, user_id)` raising `not_crew_member` 403, placed before the first `db.session.add` |
| T-05-26 | Repudiation | recognition-ledger rows with no membership basis | medium | mitigate | The guard precedes the write, so a refused award leaves no `ContributionPoint`; asserted by a count query, not by a status code |

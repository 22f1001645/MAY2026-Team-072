<objective>
Give the three Phase 7 surfaces one typed, adapted, cached read of the progression endpoint. `ProposalNew` will call it with a city to drive the fest-card lock; `OrgProfile` will call it without one to drive the sponsorship banner. Both go through a single hook over a single adapter.

Purpose: this project's rule is that snake_case becomes camelCase exactly once, in `lib/api.ts`. Landing the data layer as its own plan is what keeps plans 07-04 and 07-05 from each writing their own reshaping — the two-copies-of-the-same-adapter failure that 04-06 was created to prevent in Phase 4.

Output: two exported types, one adapter, one fetch function, one query hook, and one added cache invalidation.

Decisions implemented here:
- D-04: `useOrgProgression(orgId, city)` is the live-fetch that refires whenever org or city changes on the proposal form, returning both track-record counts independently so the lock caption can name which half is missing.
- D-05: the same hook called with no `city` serves the `OrgProfile` sponsorship banner from the `unlocks` array — one endpoint, two callers, one cache family.
- D-01: `collaboratorThreshold` is carried on the response so the named-vs-accepted counters in plans 07-04 and 07-05 both read the server's constant instead of a hardcoded number.

**Wire contract.** This plan runs in the same wave as 07-02, which builds the endpoint. The contract is frozen by 07-RESEARCH.md §New Read Endpoint and restated verbatim in Task 1 below. If 07-02's summary reports a different shape, `adaptFestEligibility` in `lib/api.ts` is the single place to reconcile it — no page change is required.
</objective>

These are the same hook. **Ship `useOrgProgression`** — it matches the `useOrgProfile` sibling it is modelled on and the endpoint it calls. Plan 07-04 must import that name and must not create a second hook under the UI-SPEC's name.

# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this contract:** the eight UI surfaces Phase 3 touches (see `## Surface Contracts`). Everything else in `frontend/` is inherited and out of scope.

**Governing principle for this phase:** every token, class string and primitive named below already exists in the codebase unless explicitly marked `NEW`. This is a brownfield design system derived from the EKATVA Brand Kit v1.0. Phase 2 established the extension rules; **this phase adds zero new design-system primitives** — every surface below composes `Button`, `Card`, `Badge`, `Input`, `Select`, `Dialog`, `Progress`, `EmptyState` as they already ship.

**The one sentence that governs the whole phase:** a proposal now names *other people's organisations* and *other people by name*, and it spends *community money*. Every surface below exists to make a consequence legible before it is committed — never to add a step.

## Spacing Scale

Base unit 4px. Declared values — **8-point scale, no 12px member**:

| Token | Value | Tailwind | Usage in this phase |
|-------|-------|----------|---------------------|
| xs | 4px | `p-1`, `gap-1` | badge icon-to-label gap; chip inner padding |
| sm | 8px | `gap-2`, `mt-2`, `space-y-2` | gap between roster rows; gap between Accept and Decline; collaborator chip row gap; the action-button gap in every new card footer; budget line-row gap (matches the existing `space-y-2` in `ProposalNew.tsx`) |
| lg | 16px | `px-4`, `gap-4`, `mb-4` | invitation card padding (`p-4`); grid gap inside the admin review panel; the section-header row above each new proposal block |
| xl | 24px | `p-6`, `space-y-6` | every new proposal `Card` uses `p-6`, matching the four existing ones; gap between form sections (`space-y-6` on the existing `<form>`) |
| 2xl | 32px | `mb-8` | separation between the dashboard stat grid and the Invitations block |
| 3xl | 48px | `py-12` | empty-state vertical padding (inherited from `EmptyState`) |

**Vertical rhythm rules for this phase:**
- The two new proposal `Card` sections join the existing `space-y-6` form stack. They add **no** margin of their own — `space-y-6` owns every gap between form sections and must remain the only mechanism.
- Section order inside `ProposalNew.tsx` is **locked**: Scale → Core details → **Collaborating organisations** → **Team roster** → Line-item budget → Quota notice → Actions. Collaborators precede the roster because a roster of people is easier to reason about once you know which organisations are running it. Budget stays last because S3's ceiling depends on Capacity, which lives in Core details — a reader who scrolls linearly has already set capacity before the ceiling appears.
- The Invitations block on the organiser dashboard sits **below** the stat grid (`mb-8` above it, inherited from the existing grid's own `mb-8`) and **above** "My proposals & events". Rationale: an invitation is a request from someone else with a decision attached; your own events are not going anywhere.
- Invitation cards stack at `space-y-3` **only because they sit directly beneath, and read as a continuation of, the dashboard's existing `space-y-3` event list** (`OrganiserDashboard.tsx:65`). This is a call-site match, not a token — see the inherited-12px table below. Two adjacent lists on one page at different stack gaps would read as a misalignment, not a distinction.

**Exceptions (documented, not to be "fixed") — NOT part of the declared scale above.**

> ⚠️ The values in this table are **not tokens and not available for any new spacing decision in this phase.** Each is valid only on the one inherited primitive or call site named in its row. Every new spacing decision — new component, new gap, new margin, new padding — must come from the declared scale table above (4 / 8 / 16 / 24 / 32 / 48).

| Exception | Value | Valid ONLY on | Reason |
|-----------|-------|---------------|--------|
| `Button` vertical padding | 6px (`py-1.5` sm), 10px (`py-2.5` md), 14px (`py-3.5` lg) | the existing `Button` primitive — nothing else | Hardcoded in the `Button` base. Inherited from Phase 2's identical exception. |
| `Input` / `Select` vertical padding | 10px (`py-2.5`) | the existing `Input` and `Select` primitives — nothing else | Same, inherited. |
| `ProposalNew` local field padding | 12px vertical (`py-3`), 8px (`py-2`) on budget-line inputs | the existing local `Input`/`selectCls`/budget-row inputs in `ProposalNew.tsx` — nothing else | Pre-existing in the file this phase extends. New fields added by S1/S2 use the shared `Input`/`Select` primitives instead, so the exception does not spread. |
| Badge vertical padding | 2px (`py-0.5`) | the existing `Badge` primitive — nothing else | Inherited. |
| Row-remove button box | 36px (`w-9`, `h-9`) | the existing budget-line remove button and the roster/collaborator remove buttons that match it | Matches the existing control at `ProposalNew.tsx:202`. 36px exceeds WCAG 2.5.8 AA (24px minimum). **No icon-only control in this phase may be smaller than 36px, and none may ship without an `aria-label`** — see the copy rule and the S1/S2 remove-button rows. |

#### The inherited 12px rhythm — a closed list, not a token

12px is **not** a member of this phase's spacing scale and is **not** available for any new spacing decision. It survives only where a new element is inserted directly into, or directly beside, an existing 12px element and any other value would visibly misalign against it. That is a finite, enumerated set:

| New usage | Class | The existing call site it must match | Why 8px or 16px is wrong *here* |
|-----------|-------|--------------------------------------|-------------------------------|
| Invitations block `h2` bottom margin (S6) | `mb-3` | `OrganiserDashboard.tsx:56` — the "My proposals & events" `h2`, which S6's heading is explicitly specified to match "exactly" | Two sibling `h2`s on one page with different heading-to-content gaps read as a typo. |
| Invitation card stack (S6) | `space-y-3` | `OrganiserDashboard.tsx:65` — the event list this block sits immediately above | Two adjacent card stacks at different gaps read as a misalignment. |
| Invitation card action-row top margin (S6) | `mt-3` | `OrganiserDashboard.tsx:92` — the existing dashboard card's own action row | Same card family, same page, same shape. |
| Collaborator / roster row inner gap and padding (S1, S2) | `gap-3`, `px-4 py-3` | `ProposalNew.tsx:330` (`gap-3 … px-4`) and the local field shell at `ProposalNew.tsx:451/456` (`px-4 py-3`) — the rows S1/S2 sit between | The new rows stack in the same form column as those; a different row height makes the form look like two forms. |
| Submission-rejection strip padding (S4) | `px-4 py-3` | `ProposalNew.tsx:416` — the exact strip S4 replaces, in the exact same position | S4 is a replacement of that element, not a new one. |

**Everything else is 8px or 16px.** Specifically, and by correction of an earlier draft of this contract: the gap between action buttons in any new card footer is `gap-2` (8px, S5 and S6 both), and the collaborator chip row in S7 is `gap-2` (8px). No new `gap-3`, `mb-3`, `mt-3`, `space-y-3` or `py-3` may appear anywhere in this phase outside the five rows above.

## Typography

Four declared sizes. All are existing `tailwind.config.js` tokens except the 14px control size, the established arbitrary value throughout `ProposalNew.tsx` and `Layout.tsx`.

| Role | Size | Weight | Line Height | Token | Applied to |
|------|------|--------|-------------|-------|-----------|
| Heading | 20px | 600 | 1.4 | `text-h3` | "Invitations" block heading, dialog title, empty-state heading, admin review sub-headings |
| Body | 16px | 400 | 1.6 | `text-body` | invitation body copy, empty-state body, the reassignment consequence line |
| Control | 14px | 500 (600 when selected / when it is a value rather than a label) | 1.4 | `text-[14px]` | field values, org names, member names, role chips, button labels (`Button size="md"`), budget figures |
| Caption | 12px | 600 when a label (`uppercase tracking-wider`), 400 when a sentence | 1.5 | `text-caption` | field labels, collaborator status lines, ceiling explanation, invitation metadata |

**Weights — exactly two declared:** `400` (regular) and `600` (semibold).

**Weight exception (inherited, not introduced):** `Button` hardcodes `font-bold` (700), `SectionTitle` renders its `h1` at `font-bold`, and `Badge` renders at `font-medium` (500). All three are pre-existing brand-kit decisions. **This phase introduces zero new 700-weight text.**

**A deliberate reading of the 500 weight:** `text-[14px] font-medium` already exists across `Layout.tsx` and the notification dropdown, and `Badge` ships at `font-medium`. Treating 500 as a third declared weight would be dishonest bookkeeping. It is instead scoped: **500 is the control-row weight and appears only where the codebase already puts it** (badges, nav items, notification rows). Every *new* string this phase authors is 400 or 600.

**Page titles** on surfaces this phase touches are rendered by the existing `SectionTitle` primitive (36px / 700 / 1.2, `text-h1`, `text-gold`) and are inherited wholesale.

**Casing rules:**
- `uppercase tracking-wider` is reserved for 12px labels and eyebrows only. Never on 14px or larger.
- Organisation names, member names and city names are **rendered exactly as stored** — never uppercased, never title-cased in CSS. A `text-transform` on user data corrupts acronyms (`IITM BS`) and proper nouns.
- Team role names render exactly as they appear in `constants.TEAM_ROLES` — `Meetup Head`, `Co-Head`, `Video/Content`, `PR & Outreach`. The frontend never re-cases or re-spells them; the string is the contract with the server's unique index.

**Teal accent is reserved for exactly these elements in this phase:**
1. Primary CTAs — **Submit for approval**, **Accept**, **Add to team**, **Reassign**
2. The selected activity-scale card (`border-teal bg-teal/10` — existing, unchanged)
3. Focus rings — `focus:ring-2 focus:ring-teal/50` on every interactive element in this phase, without exception

6. The **Primary** marker on the primary collaborating organisation

**Teal is explicitly forbidden on:**
- the **Mega Meetup** badge — it is gold. Mega Meetup is a *recognition*, not an action, and teal would make it read as a control.
- the budget ceiling meter's fill while **at or under** the ceiling — that is the neutral state and uses `Progress tone="teal"`'s counterpart only as described in S3; a ceiling is not an achievement.
- collaborator status chips (`pending` / `accepted` / `declined` use neutral / success / danger)
- any disabled control, in either the unauthorised or the busy variant
- decorative dividers, card borders, or section rules

**Status color mapping — locked, and never the only channel:**

| State | Badge tone | Label rendered | Second channel |
|-------|-----------|----------------|----------------|
| Collaborator `pending` | `warn` (amber) | **Awaiting reply** | the word itself, plus a `title` with the invite date |
| Collaborator `accepted` | `success` (emerald) | **Accepted** | the word, plus the responded date beneath |
| Collaborator `declined` | `danger` (red) | **Declined** | the word, plus the responded date beneath |
| Primary organisation | `teal` | **Primary** | the word, plus first position in the list |
| Mega Meetup | `gold` | **Mega Meetup** | the word, plus the count line beneath it |
| Budget over ceiling | — | see S3 | red total **and** an explanatory sentence **and** a red meter |

**Gold budget:** gold already carries every `h1`/`h2` in the app plus the existing budget-total badge. This phase adds exactly **one** new gold element — the Mega Meetup badge. No third gold surface may be added in Phase 3.

**Contrast floors (AA, verified against `#030907` / the card gradient):**
- `text-offwhite` `#F8F8F8` — primary text, all user-supplied names and values
- `text-graytext-light` `#AAAAAA` — secondary text, ≥14px only. **Never** on 12px captions carrying required information (the ceiling explanation and collaborator status lines therefore use `text-graytext-light` at 12px only because they are `font-normal` sentences duplicated by a badge; anything that is the *sole* carrier of meaning goes to `text-offwhite`).
- `text-graytext-mid` `#666666` — decorative and tertiary only (placeholders, hints, timestamps). **Never** the sole carrier of a state, a label, or an instruction.
- `text-teal` and `text-gold` both clear 4.5:1 on `bg-onyx`.
- `text-red-300` `#FCA5A5` and `text-amber-300` `#FCD34D` both clear 4.5:1 on `bg-onyx` and on the `Card` gradient.

**Never encode state in color alone.** Every row of the status table above carries a text label plus at least one further channel. This is not a style preference in this phase — a collaborator's `pending` vs `accepted` state determines whether the Mega Meetup label applies and whether a fest threshold is met, so a colour-only distinction would make a *business rule* invisible to a colour-blind organiser.

### Primary visual anchor

**Proposal form (`/proposals/new`):** the anchor is the existing `SectionTitle` ("New Proposal", 36px/700 gold). Rank order: **(1) `SectionTitle` → (2) the selected scale card → (3) the budget total + ceiling readout → (4) everything else.** The ceiling readout is deliberately third: it must be findable at a glance while filling the budget, but it is a guardrail, not the task.

**Enforceable consequence:** if the ceiling readout ever out-shouts the title in review, the fix is to quiet the readout, **never** to enlarge `SectionTitle` — which is inherited and shared by 20 pages.

**Organiser dashboard:** the anchor stays `SectionTitle` ("Organiser Dashboard"). The Invitations block ranks **second**, above the stat grid in attention but below it in document flow — achieved by the count badge and the `Accept` button being the only teal controls in that region, not by enlarging the block. When there are zero invitations the block does not render at all and the ranking question does not arise.

### Copy rules that apply to every string in this phase

- **Never say "you can't."** An unauthorised control names who *can*: **Only the Meetup Head can do this.** (Phase 2 pattern, inherited.)
- **A rejection reason is the server's sentence, shown verbatim, under our heading.** ROADMAP criterion 3 requires "the reason shown, not a generic error". The heading is ours and is specific per failure kind; the body is `error.message` from the `{ error, code }` envelope. Never replace a server reason with a paraphrase — the server knows the actual number.
- **Counts are always written out with their threshold.** "2 of 3 accepted", never "2 accepted". A count without its target is trivia.
- **Money is always `inr()`.** No bare integers, no `₹` concatenated by hand, no `toLocaleString` at a call site.
- **The bare "Cancel" exception, re-checked against this phase rather than assumed.** Phase 2's rule is that a dismiss control is labelled **Cancel** rather than **Cancel {noun}** when it is one of exactly two buttons in a dialog the user opened deliberately, and dismissing it changes nothing. Phase 3 uses **Cancel** in exactly one place — S8's reassignment `Dialog` — and it satisfies all three conditions: two buttons (**Cancel** / **Reassign**), opened by an explicit click on a reassign control, and closing it leaves the current Meetup Head untouched. Nothing else in this phase is labelled **Cancel**; S1's and S2's dismiss-equivalents are the 36px remove buttons, which are labelled by their `aria-label` per those surface contracts.
- **Every icon-only control carries an accessible name.** No control in this phase may communicate its action through a glyph alone: each takes an `aria-label` (and a matching `title`) naming the object it acts on — **Remove {Org name}**, **Remove {Name}**. This is in addition to the 36px minimum box, not instead of it.

### Forbidden vocabulary in user-facing strings

Never render to a user: `POR`, `capability`/`capabilities`, `token`, `JWT`, `401`, `403`, `422`, `is_meetup_head`, `can_manage_activity`, `activity_collaborators`, `is_primary`, `COLLAB_PENDING`, `org_id`, `payload`, `mutation`. These are implementation words. Phase 2's D-12 POR-literal build scan already structurally enforces the first; the rest are enforced by review of this table.

**One consequence worth stating:** the user-facing word for an `Activity` is **event**, and for an `Organisation` it is **organisation** (never "org" in prose — "org" is acceptable only inside a 12px label where space is genuinely constrained, e.g. a table header).

## Interaction States

Inherited wholesale from Phase 2's contract, with this phase's instances named. The disabled-because-unauthorised vs disabled-because-busy distinction is the same, and must never blur.

### A — Not permitted (capability absent)

**Default: do not render.** A user who cannot manage an activity never sees its roster controls.

**Render-locked exception**, permitted only when removing the control breaks a layout the user reads as a list, or when the user could plausibly acquire the capability:

| Channel | Value |
|---------|-------|
| Disabled attributes | `disabled` **and** `aria-disabled="true"` |
| Visual | `opacity-40 cursor-not-allowed` (inherited from `Button`'s disabled base) |
| Marker | A 12px padlock glyph immediately before the label |
| Explanation | A **visible** line beneath, `text-caption text-graytext-light`: **Only the Meetup Head can do this.** — plus the same string as `title`. A tooltip alone is unreachable on touch. |
| Pointer events | Stays hoverable and focusable. **Never `pointer-events-none`.** |
| Label | Unchanged. Never gains an ellipsis or a spinner. |

**Phase 3's live instance:** a team member who is not the Meetup Head, viewing a campaign-approval control on the event-manage surface, gets the render-locked treatment — because they *could* be made Meetup Head (S8), which is exactly the "plausibly acquire" condition. Every other unauthorised control in this phase is simply absent.

### B — Busy (request in flight)

| Channel | Value |
|---------|-------|
| Disabled attributes | `disabled` **and** `aria-busy="true"`. **Never** `aria-disabled` — it is working, not unavailable. |
| Visual | `disabled:opacity-40` from the `Button` base. No padlock, no explanatory line. |
| Label | Present-participle form of its own verb: "Accept" → **Accepting…**, "Decline" → **Declining…**, "Add to team" → **Adding…**, "Reassign" → **Reassigning…**, "Submit for approval" → **Submitting…** (the existing label at `ProposalNew.tsx:239`, unchanged) |
| Minimum duration | 300ms visible |
| Scope | Sibling controls in the same card go `disabled` for the duration; unrelated controls elsewhere on the page do not. Accepting one invitation must not freeze the other invitation cards. |

### The discriminator, stated for the reader

> A **busy** control keeps its own verb and gains an ellipsis.
> An **unauthorised** control keeps its label unchanged, gains a padlock, and gains a sentence naming who *can*.

Never both, never in the same frame.

### C — Blocked by a fixable precondition

**Submit controls stay enabled when the form is incomplete.** **Submit for approval** is never pre-disabled for a missing Meetup Head or an over-ceiling budget. The server rejects, S4 names the reason, the section is marked. A pre-disabled submit leaves the user with no way to ask *why* — and on a form this long, with two new sections, "why is the button grey" is a far worse dead end than one round trip.

This is the one rule in this phase most likely to be "helpfully" broken during implementation. It is deliberate.

### Focus and motion, globally

- Every interactive element added in this phase carries `focus:outline-none focus-visible:ring-2 focus-visible:ring-teal/50`. No exceptions.
- All transitions use `duration-200 ease-material` (`cubic-bezier(0.4, 0, 0.2, 1)`).
- `prefers-reduced-motion` is handled app-wide in `index.css`; no component-level handling is needed or permitted.
- The member search results list is keyboard-navigable: `ArrowDown`/`ArrowUp` move, `Enter` selects, `Esc` clears. A search that requires a mouse is a search half-built.

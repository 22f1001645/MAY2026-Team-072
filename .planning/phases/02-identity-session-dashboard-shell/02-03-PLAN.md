## Verified state (2026-08-12) — what already exists in `auth_service.refresh`

The rotation state machine is **written and structurally close to correct**, and until 02-01 it had never executed. Read `backend/app/services/auth_service.py` lines 74-115 before changing anything. Its current shape:

1. If `family_revoked(fam)` → raise 401 `session_revoked`.
2. Else if the presented `jti` is already in the blocklist → if the row is older than 10 seconds, write a `reuse_detected` tombstone and raise 401; **otherwise fall through** and re-issue.
3. Else → write a `rotated` row for the presented `jti`.
4. Mint a new refresh token carrying the **same** `fam`.

`BlocklistRepository.family_revoked` correctly treats `rotated` as non-revoking — it filters `reason != "rotated"` — so ordinary rotation does not revoke its own family. That subtlety is right and must not be "simplified".

**Three real defects in that block, to fix here:**

- **The grace window is the inline literal `10`** at `auth_service.py:90`. CLAUDE.md requires business constants in `constants.py`. It is also undocumented, so nothing connects it to D-02a or to ROADMAP criterion 2.
- **The reuse tombstone reuses a synthetic jti**, `"fam_" + family_id`. `RefreshTokenBlocklist.jti` is `unique=True`, so detecting reuse **twice** on the same family raises `IntegrityError` → 500. `logout` has the identical shape with a `"logout_"` prefix, so logging out twice on one family has the same failure.
- **The D-02a semantics differ subtly from the code.** D-02a says a replay inside the window "returns the already-issued successor". The code mints a *new* token in the same family instead. That is acceptable and simpler — both tabs end up with valid tokens in one family — but it is an undocumented deviation from a locked decision and must be recorded, not silently kept.

`revoked_at` is written by `BlocklistRepository.add_entry` via `datetime.utcnow()` (naive UTC) and compared against `datetime.now(UTC).replace(tzinfo=None)` in the service. The two agree today. `datetime.utcnow()` is deprecated and already emits warnings in the suite; since this plan edits that method anyway, modernise it — but keep both sides naive-UTC so the comparison stays valid.

**Out of scope, present in the tree:** the "Phase 9 admin analytics" feature from commit `f2c127e`. Do not extend or test it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `POST /auth/refresh` | A 30-day bearer cookie is exchanged for a fresh access token; the only defence against a cross-site POST is the double-submit CSRF token |
| stolen refresh token → live session | Reuse detection is the sole control that limits a stolen token's blast radius below its 30-day lifetime |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-02 | Spoofing | `POST /auth/refresh` | high | mitigate | Built-in double-submit CSRF (`X-CSRF-TOKEN` vs the in-JWT `csrf` claim, constant-time); Task 3 tests rejection with a negative control |
| T-02-03 | Spoofing / elevation | `auth_service.refresh` reuse branch | critical | mitigate | Replay outside the grace window writes a family tombstone; Task 2 asserts the live successor is also killed, not just the replayed token |
| T-02-05 | Spoofing | `auth_service.login` family minting | high | mitigate | A new `fam` is minted per authentication; Task 2's independent-families test asserts one family's revocation leaves the other usable |
| T-02-04 | Elevation | 30-day refresh lifetime | high | mitigate | Server-side blocklist consulted on every refresh, never gated on token expiry |
| T-02-18 | Denial of service | grace-window false positives | high | mitigate | `REFRESH_ROTATION_GRACE_SECONDS` re-issues rather than revoking inside 10s, so two tabs waking together do not log the user out. Widening it is prohibited: window width is replay window width |
| T-02-19 | Denial of service | duplicate family tombstone | medium | mitigate | `revoke_family` builds a collision-free synthetic jti, so a second reuse detection cannot raise `IntegrityError` into a 500. NEW threat, found in the 2026-08-12 audit |
| T-02-20 | Denial of service | blocklist loader on every request | medium | mitigate | Access-token short-circuit keeps the loader out of the database on ordinary API calls; Task 3 pins it with a mutation-verified counter |
</threat_model>

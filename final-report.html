Key Research Findings

Open chat is an anti-feature

Research showed peer-to-peer chat creates moderation burden disproportionate to value. The platform uses a Swiggy-support-ticket model: organiser broadcasts + polls only. Registrants can query. No peer-to-peer reply.

Photos cannot be trusted for attendance

Any person can appear in a group photo. QR-verified digital check-in is the sole authoritative count. Photo links are supplementary evidence only — never used for point awards or reimbursement verification.

Section 04

User Stories & System Requirements

Eight operational epics structuring the platform's functionality — derived from stakeholder interviews.

Epic 1 — Proposal & Approval

As an Event Lead, I want to submit a standardised proposal with title, date, venue, capacity, and itemised budget so that my proposal enters an official review pipeline.
As an Admin, I want to approve, request modifications, or reject proposals with recorded feedback notes and a tamper-proof audit trail.

Epic 2 — Task Workspace

As an Event Lead, I want a shared Kanban task board to delegate duties with deadlines to team members.
As a Volunteer, I want to view my assigned duties across events and update task statuses (To Do → In Progress → Review → Done).

Epic 3 — Regional Quota Guardrails

As an Administrator, I want automated quota enforcement (max 1 meetup per region per calendar month) to prevent event crowding.

Epic 4 — Notifications

As an Event Lead, I want to broadcast urgent announcements (venue/timing changes) to all registered attendees in one click.
As a Student, I want an in-app notification centre for real-time updates on events I have registered for.

Epic 5 — Budget & Reimbursement

As an Event Lead, I want to attach itemised budget categories to my proposal and upload receipts post-event.
As an Admin, I want to advance expense claims through: Submitted → Verified → Approved → Paid.

Epic 6 — POR Governance

As an Administrator, I want to assign and deactivate student leadership roles, maintaining an immutable audit history of transitions across terms.

Epic 7 — Gamification & Points

As a Student, I want to earn verified contribution points for attending (30 pts), organising (50 pts), or volunteering (20 pts), and see my rank on city and overall leaderboards.

Epic 8 — Post-Event Analytics

As an Administrator, I want an analytics dashboard showing attendance retention, active vs. dormant learners, and activity fee utilisation rates by region.
Section 05

Product Principles

Eight non-negotiable design principles from PRD v2.2 — honoured in every technical decision and enforced where possible by build-gate tests.

1
Community before organisation before activity
The platform serves communities first. Organisations are containers. Activities are the vehicle — never the goal.
2
Belonging is the outcome
Friction-removal is the job. Every feature is judged by whether it helps someone feel more connected to their community.
3
Permissions follow PORs, not logins
Two login roles only: Admin and Student. All organiser capability is derived from POR — never a third login type. Enforced by a no-por-literals build-gate test.
4
Knowledge must survive leadership
POR holders turn over every term. Immutable audit logs capture decisions, budgets, and event histories so institutional knowledge persists across cohorts.
5
Operations should be invisible
The best ops platform is one where the organiser doesn't feel like they're using a platform. Automate away every repeatable step.
6
Every contribution is visible
Attendance, volunteering, organising — every act of participation earns points and appears on a leaderboard. No invisible labour.
7
Evidence over untested assumption
QR-verified attendance, not photo headcounts. Server-enforced budget caps min(capacity×₹200, ₹20,000), not honour-system limits.
8
Design for turnover and scale
40,000 students today, growing fast. Architecture, permissions, and data models are built for a programme that doubles — not one that stays still.

6.1 POR-Based RBAC — Deny-by-Default

Four resource-scoped predicates replace the coarse @organiser_required guard. Every new endpoint uses these — no org-wide or role-wide blanket access. 

# Resource-scoped predicates in rbac.py
can_manage_activity(user, activity)    # Team member or org authority
can_participate_in_activity(user, act)  # Registered attendee
can_manage_org(user, org)              # Secretary/Deputy of THIS org
is_meetup_head(user, activity)          # Campaign push-live authority

6.2 JWT Authentication Flow

Short-lived access tokens (15 min) + long-lived HttpOnly refresh cookies (30 days). Token rotation on every refresh with replay detection — if a stolen token is used, the entire family is invalidated. A 10-second multi-tab grace window prevents concurrent refreshes from logging users out. Single-flight interceptor ensures only one refresh call at a time.

Section 14

Challenges Faced & Key Technical Learnings

Challenge 1 — Dynamic Resource-Scoped Authorisation vs. Static Login Roles

Problem: A student's authority changes dynamically based on active PORs and event crew assignments. Static JWT claims become stale immediately after a POR handover.

Solution: Four authorisation predicates (can_manage_activity, can_participate_in_activity, can_manage_org, is_meetup_head) evaluate live from the database on every request. /auth/me returns server-computed capabilities; the frontend POR list was eliminated with a no-por-literals build-gate test.

Challenge 2 — Race Conditions on Event Waitlists

Problem: Concurrent registrations when an event has 1 remaining seat could cause over-capacity bookings.

Solution: Transactional check-and-reserve logic in registration_service.py immediately routes excess registrants into sequential waitlisted status. Database-level UNIQUE (activity_id, student_id) constraint acts as a safety net.

Challenge 3 — Database Migration Safety on SQLite

Problem: SQLite has limited native support for table alterations (e.g., dropping columns) — Alembic's standard ALTER TABLE migrations fail.

Solution: Configured Alembic batch migration mode (render_as_batch=True in env.py). Enables seamless schema evolution via table-copy-swap without data loss. 16 new tables and 11 columns were added in a single batch migration.

Challenge 4 — Preventing QR Attendance Fraud

Problem: A single event QR code displayed at the venue is a fraud vector — anyone can photograph it and check in remotely.

Solution: Flipped the model: each registration generates a unique signed short-TTL QR token. Attendees display their personal token; any team member scans it. Re-scan is idempotent (caught via UNIQUE registration_id constraint). Photo links remain supplementary only — never authoritative.

Challenge 5 — AI Feature Reliability

Problem: The Gemini API can be unavailable, unkeyed, or rate-limited — making AI-dependent features unreliable for a graded project.

Solution: Every AI feature was built with explicit graceful degradation. The brand kit editor and campaign mail generator each return a usable static template when the API key is absent or the call fails, gated behind a 503 Degraded response the frontend handles transparently.

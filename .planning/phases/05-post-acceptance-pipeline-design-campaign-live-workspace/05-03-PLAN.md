<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Decide the campaign state machine — two states or three</name>
  <decision>Does Phase 5 ship `draft → live`, or `draft → pending_approval → live` with an explicit "submitted for Meetup Head approval" step?</decision>
  <context>
`CAMPAIGN_PENDING_APPROVAL = "pending_approval"` is already declared in `constants.py` and
already in the `CAMPAIGN_STATES` tuple, so both options are schema-legal with no migration.
None of the SPEC's 38 acceptance criteria requires the intermediate state to be reachable —
AC-24 asserts one transition to `live` that sets `approved_by`, `approved_at` and
`pushed_live_at` together. But D-06's 5-step pipeline stepper ends at "Meetup Head Approval",
and if there is no submit action, step 5 is a button rather than a state, which may read as
misleading to an organiser who is not the Meetup Head.

This is the phase's one **one-way** decision: campaign status values land in rows in the dev
database and, once an event is live, in whatever a marker's demo run produces. Reversing means
a data fix, not a code change. (05-RESEARCH.md Assumptions Log A3 flagged exactly this and
recommended asking rather than assuming.)
  </context>
  <options>
    <option id="option-a">
      <name>Two states: draft → live</name>
      <pros>Fewest moving parts; matches AC-24 verbatim; `pending_approval` stays declared-but-unused exactly as `EXPENSE_DRAFT` already is (`constants.py:176-184`), which is an established precedent in this codebase; nothing else in Phase 5 or Phase 6 reads the intermediate state.</pros>
      <cons>D-06's step 5 "Meetup Head Approval" shows as incomplete until the moment of publication, with no way for a non-Meetup-Head member to signal "the package is ready for you".</cons>
    </option>
    <option id="option-b">
      <name>Three states: draft → pending_approval → live</name>
      <pros>A non-Meetup-Head team member can mark the package submitted, so the stepper's step 5 has a real intermediate state and the Meetup Head has an inbox-like signal.</pros>
      <cons>Adds a second endpoint, a second authorization question (who may submit?), a second set of tests, and a state a future phase must handle; no acceptance criterion asks for it.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a or option-b</resume-signal>
  <reversibility rating="one-way">Campaign status values persist in `campaign_packages.status`. Once rows carry a value, changing the machine is a data migration, not a code edit.</reversibility>
  <read_first>

    - backend/app/models/__init__.py:684-724 (`CampaignPackage.status`, `approved_by`, `approved_at`, `pushed_live_at` and the docstring explaining why approval fields are kept separate from `pushed_live_at`)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api/v1/.../campaign/push-live` | The publication boundary — everything student-visible is downstream of this call |
| `meetup_head_required` → view | The one place a *specific* person, not a role, is required |

## STRIDE Threat Register (ASVS L1, block on high)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-14 | Elevation of Privilege | non-Meetup-Head publishing via a direct API call | critical | mitigate | `@meetup_head_required` = `activity_scoped(is_meetup_head)` with no admin short-circuit and no `can_manage_activity` fallback; `test_push_live_non_meetup_head_403` is the negative control and asserts the persisted state, not only the status code |
| T-05-15 | Elevation of Privilege | an admin acting as the Meetup Head | high | mitigate | Same predicate; the admin case is asserted explicitly in Task 3. Phase 1 already ships a source assertion that `ROLE_ADMIN` never appears in `is_meetup_head` |
| T-05-16 | Spoofing | a client trusting or forging its own `is_meetup_head` flag | medium | mitigate | The flag is computed server-side from `rbac.is_meetup_head` and is advisory for rendering only; the route guard is the enforcement and refuses regardless of what the client sent |
| T-05-17 | Repudiation | a publication with no attributable approver | medium | mitigate | `approved_by` / `approved_at` are written in the same commit as `pushed_live_at` and asserted non-null by AC-24 |
| T-05-18 | Tampering | re-stamping the approval trail by replaying push-live | medium | mitigate | The already-live branch returns before any assignment or commit; AC-26 asserts the timestamps are byte-identical across two calls |
| T-05-19 | Tampering | publishing an incomplete package (no agenda) | low | mitigate | `assert_schedule_non_empty` reused from plan 05-01 — one definition of "empty schedule", not two |
| T-05-SC | Tampering | package-manager installs | high | accept | This plan runs no `pip install` / `npm install`; Phase 5 adds zero dependencies |
